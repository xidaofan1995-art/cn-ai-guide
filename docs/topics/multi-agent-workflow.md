# 个人多Agent工作流全景：主控、执行员、审核员与数据管家

**B02 · AI工具与工作流 · 初稿 / 方案研究 · 2026-11-27**

> 本页为公开初稿，可持续修订；作者未补充的个人观点留空，构造案例、AI建议与实际测试分开。动态信息在后续更新前复核。

![从单Agent到多角色协作的最小闭环](/images/topics-b02.svg)

## 30秒概览

1. 多 Agent 的价值来自任务分工、独立审核或权限隔离，而非数量。
2. 先跑通一个任务，明确共享状态，再增加角色；一个人可以兼任审核员。
3. 对外发送、付款、删除或覆盖正式版本，必须设人工授权闸门。

## 5分钟理解与决策

| 角色 | 输入 | 输出 | 权限边界 |
| --- | --- | --- | --- |
| 主控 | 目标、约束、任务清单 | 派工、成功标准、状态 | 不代替业务审批 |
| 执行员 | 指定任务及材料 | 草稿、证据、执行日志 | 只写指定工作区 |
| 审核员 | 草稿、来源与验收条件 | 通过、问题、返工意见 | 审核不等于批准高风险动作 |
| 数据管家 | 已确认结果与版本 | 索引、台账、归档记录 | 不改作者原始输入 |

四类是职责，不要求四个不同模型。单 Agent 配人工核对就能处理许多工作；如果需要不同证据来源、独立复核或并行任务，再拆角色。

### 一个最小内容生产示例

假设任务是从公开资料写一篇科普：主控固定问题和资料范围，执行员查来源及写草稿，审核员检查关键断言和图表，作者批准指定版本，数据管家记录 URL 与版本。这个例子是建议工作流，并非真实运行成功记录。

状态机应允许明确的退回与失败，而不是只画一条向前的线：

| 当前状态 | 合法转移 | 触发条件 |
| --- | --- | --- |
| 待执行 | 执行中 | 领取任务且未被其他人领取 |
| 执行中 | 待审核 / 失败 | 产物齐备或重试达到上限 |
| 待审核 | 待返工 / 待批准 | 审核记录明确 |
| 待批准 | 发布中 | 人批准具体版本 |
| 发布中 | 已发布 / 失败 | 线上核验成功或记录失败原因 |
| 失败 | 待执行 / 暂停 | 人或规则允许重试 |

## 深度探索：共享状态比角色名称更重要

每个任务至少记录 task_id、输入版本、执行人、run_id、当前状态、产物链接、失败原因、重试次数、时间。使用任务唯一键和预期版本校验，避免两名执行员同时覆盖正式结果。相同任务重试时应尽量更新同一记录，不重复发信或新建资产。已经产生副作用的动作不能盲目重试。

权限分离也很重要：执行员可以写草稿但不能删除历史版本，审核员可提出修改但不能冒充作者，主控可派工但不能无限调用有费用的服务。用 Git 变更评审作为版本协作参考，[GitHub Pull Request 文档](https://docs.github.com/en/pull-requests/reference/pull-requests)（2026-11-27），具体实现随工具而异。

### 什么时候不要使用多Agent？

如果任务一次即可完成、输入不稳定、无法定义验收，或协调开销超过单人工作的收益，先使用单 Agent 加检查表。跟踪总尝试次数、完成率、重试、人工修订时间，不只展示成功案例。
